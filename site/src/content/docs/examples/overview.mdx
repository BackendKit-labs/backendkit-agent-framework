Every example here runs on the current framework, shows **the code that makes it work** (not only how to start it) and has a way to check it **without trusting a model**. They are grouped by what they teach; inside each group, read them in order.

## Start here: small and offline

Four small examples in the `examples/` folder of the monorepo. Each adds one idea to the previous one.

| Example | What it teaches | You need |
|---|---|---|
| [`flows`](../flows/) | A process as data: a journal, an approval, a resume. No model, so you see the engine alone | Node |
| [`git-agent`](../git-agent/) | A real agent in a terminal: your own safe tools, a team with delegation, a read-only switch, a typed result, a budget | A model key (the checks need none) |
| [`git-analyst`](../git-analyst/) | An agent **served over MCP** that other programs call | A model key |
| [`vault-pilot`](../vault-pilot/) | **Knowledge agents**: department agents answering from a shared vault, each limited to its own folders | A model key (the checks need none) |

## Governance and autonomy: agents that act on real things

The two examples where an agent can **spend or move something that cannot be undone**, and the framework is what keeps it inside its limits.

| Example | What it teaches | You need |
|---|---|---|
| [`portfolio-advisor`](../portfolio-advisor/) | The reference: identity, a **signed power** with limits, approval by role and four eyes, a signed audit, a durable flow, MCP, the agent protocol and evaluations, all from the framework | Node |
| [`aval-scheduler`](../aval-scheduler/) | An **autonomous agent that pays**: cron, webhook and an MCP data source, paying only through AVAL, and a test that proves it pays once | Node (a model key to run it for real) |

## Flows and teams: the deep dives

Larger programs, in the `agent-framework-examples` repository. Each one found real problems in the framework, and they were fixed there.

| Example | What it teaches | You need |
|---|---|---|
| [`research-desk`](../research-desk/) | Several agents as a flow: parallel analysts, a decision, an approved action, **memory and learning** | A model key |
| [`release-captain`](../release-captain/) | A **model that supervises flows**: several at once, and it cannot approve its own report | A model key |
| [`audit-desk`](../audit-desk/) | Flows **across processes** against a real Redis, surviving a hard kill | Docker (for the Redis part) |

## What they have in common

Every example has a check that does not need a model: `git-agent` has 8 offline checks, `vault-pilot` 7, `portfolio-advisor` 60 tests, `aval-scheduler` an end-to-end test with a scripted model, and the deep dives have offline suites. The monorepo's CI **installs each small example from its lockfile and runs it** on every pull request, so an example that stops matching the published packages fails there. That is the pattern to copy in your own agents.

<Aside type="note" title="Why only these">
There are more programs in the repositories, but an example is listed here only if it runs on the current framework and teaches something the others do not. `mandate-agent` (an adapter for an identity provider's credential, over an assumed format) is in the repository too, and waits for that provider's real format before it is written up.
</Aside>

## How the deep dives improved the framework

Writing a real program is the best test of a library. The examples found real problems, and each was **fixed in the framework**, not worked around in the example:

- the research desk showed a flow claim that was not renewed on a long run, and no way to skip a step conditionally (`when`);
- the audit desk showed a queue that could lose the completion of an instant step, and a file journal that failed under a wide fan-out;
- the release captain showed that a hosted flow with a human gate ended `failed` instead of waiting, and that a supervising model had no way to wait without polling (`flow_wait`);
- the portfolio advisor showed that the record of an approval had no reason, that flows and the tool server did not enforce roles and four eyes the way the engine did, and that a mandate was asked for even to read.

If you build something with the framework and hit a wall, that is useful: the answer is usually a change in the framework, not a trick in your code.
