## In plain words

**What it is.** Two ways to make several agents work together: **delegation** (an agent asks another through `ask_agent` and the model decides who and when) and **flows** (you decide the path in advance).

**Why you need it.** One agent that knows every domain and holds every tool does worse and can do more harm than a team of specialists, each with its own tools and its own identity. Splitting also lets you give the dangerous tool to one agent only.

**How it works here.** An agent whose profile lists `delegatesTo` can hand a sub-task to a named agent. The engine runs the other agent and returns its answer. The specialist acts under **its own** identity and permissions, and the chain records who asked. When the order must be the same every time, you write a flow instead.

**What it does not do.** Delegation does not lend power: the orchestrator's permissions are not the specialist's, and the specialist does not inherit the orchestrator's. It is also **not deterministic**: the model chooses who to ask, so if the order matters or something must stop for a person, use a flow.

**In one line.** Delegation is **the model choosing who to ask**; a flow is **you choosing the path**.

## Delegation: an agent asks another

The default agent hands a sub-task to a named agent through the `ask_agent` call. The engine runs the other agent and returns its answer.

`delegatesTo` is a limit, not a hint. With a list, the engine refuses (and audits as `not_allowed`) a delegation to any agent outside it, and the agent roster in the prompt shows only those agents. `['*']` means every registered agent. Without a list, or with an empty one, the default agent may delegate to every other agent. An agent that an MCP server registers in `mode: 'agent'` is always reachable, because configuring that server already declared it. Only the default agent receives `ask_agent`: a specialist does not delegate, whatever its `delegatesTo` says.

A tool can delegate too, with `ctx.askAgent(agentId, question)`. It goes through the same check, for the agent that runs the tool, and is audited the same way; a refusal throws.

```ts
const orchestrator: AgentProfile = {
  id: 'orchestrator', name: 'Orchestrator', icon: '🧭', description: 'Routes requests',
  systemPrompt: 'Route each request to the right specialist.',
  allowedTools: [],
  delegatesTo: ['billing', 'support'],        // or ['*'] for every registered agent
};
```

A complete team, runnable offline. The specialist owns the tool; the orchestrator owns none and only decides who answers. One scripted model plays both agents, in the order they speak:

```ts
import { createBaseEngine, defineTool, z, type AgentProfile, selfAssertedIdentities } from '@backendkit-labs/agent-core';
import { scriptedProvider, mockTransport } from '@backendkit-labs/agent-testkit';

const invoiceTotal = defineTool({
  name: 'invoice_total', description: 'Total of an invoice', readOnly: true,
  input: z.object({ invoiceId: z.string() }),
  execute: async ({ invoiceId }) => `Invoice ${invoiceId}: 1,250.00 EUR`,
});

const billing: AgentProfile = {
  id: 'billing', name: 'Billing', icon: '🧾', description: 'Answers questions about invoices',
  systemPrompt: 'You answer questions about invoices. Use invoice_total.',
  allowedTools: ['invoice_total'],
};
const orchestrator: AgentProfile = {
  id: 'orchestrator', name: 'Orchestrator', icon: '🧭', description: 'Routes each request to a specialist',
  systemPrompt: 'Route each request to the right specialist with ask_agent, then give the answer to the customer.',
  allowedTools: [],
  delegatesTo: ['billing'],
};

const engine = createBaseEngine({
  agentIdentity: selfAssertedIdentities(),   // who the agent is (SPEC-0044)
  identity: { userId: 'me' },                // on whose behalf it acts
  providers: { mock: scriptedProvider([
    { tool_calls: [{ id: 'a1', name: 'ask_agent', args: { agent_id: 'billing', question: 'What is the total of invoice INV-7?' } }] },
    { tool_calls: [{ id: 'b1', name: 'invoice_total', args: { invoiceId: 'INV-7' } }] },
    { content: 'The total is 1,250.00 EUR.' },                 // billing answers the orchestrator
    { content: 'Invoice INV-7 comes to 1,250.00 EUR.' },        // the orchestrator answers the customer
  ]) },
  defaultProvider: 'mock', agents: [orchestrator, billing], defaultAgent: 'orchestrator',
  tools: [invoiceTotal], transport: mockTransport().transport, workingDir: process.cwd(), iterationMode: 'auto',
});

const result = await engine.run('How much is invoice INV-7?');
console.log(result.text);                                        // Invoice INV-7 comes to 1,250.00 EUR.
console.log(result.toolCalls.map(c => `${c.name}:${c.success}`)); // [ 'invoice_total:true', 'ask_agent:true' ]
```

`result.toolCalls` includes the calls of the delegate: that is how a test proves the specialist, and not the orchestrator, did the work.

- Delegation has a **depth limit** and a recorded **delegation chain**, so a loop of agents asking each other stops, and the policy knows who asked whom.
- A delegation is a call like any other: a [policy](../governance/) can allow, ask or deny it.
- Calls to `ask_agent` in the same turn can run in parallel.

Use it when the *model* should decide who handles what, and the path is not known in advance.

## Flows: you decide the path

When the steps are known (collect, check, report, approve), do not ask a model to remember them. Write a [flow](../flows/): a YAML file of steps and dependencies that the engine runs, journals and resumes. Each step is run by an agent, but *which* steps run, in what order, and where a person must approve is data, not a prompt.

| | Delegation | Flow |
|---|---|---|
| Who plans the path | The model, as it goes | You, in a file |
| Survives a crash | No | Yes (journal) |
| Parallel steps | Calls in one turn | Declared by dependencies |
| Human approval | Through the policy | A `gate` on a step |
| Best for | Open-ended requests | Business processes |

The two combine: a flow step can be a conversation with an agent that itself delegates.

A third option, the `workflow()` builder, sequences agent steps in code. It predates flows and has no journal; prefer flows for anything that must not be lost.
