## In plain words

**What it is.** The **Model Context Protocol** lets programs share tools. The framework speaks it both ways: it can **use** the tools of an MCP server, and it can **serve** its own tools to any MCP client, with or without a model in between.

**Why you need it.** Without a shared protocol each integration is an adapter you write. With it, someone else's tools show up in your engine next to yours, and yours become available to scripts, jobs and other agents that never heard of your framework.

**How it works here.** As a client you give the engine `mcpServers`; their tools appear with a prefix (`mcp__<server>__<tool>`) and go through the same checks as any tool. As a server `createToolServer` exposes your tools so that the arguments the client sends are the ones `execute` receives, with no model.

**What it does not do.** A tool that comes from outside is **not trusted** by default: the client does not believe a server that says a tool is read-only unless you set `trustAnnotations`, so an unknown tool asks a person. A directly served destructive tool will not start without an `authorize` function or a policy. And MCP authenticates nobody: who the caller is stays yours to verify.

**In one line.** MCP is **how tools cross the boundary of a program**, and the framework checks them on both sides of it.

## As a client: use someone else's tools

Give the engine MCP servers and their tools appear next to yours. The client can watch the connection and report when a server drops.

## As a server, without a model

`createToolServer` exposes your `ToolDefinition`s as MCP tools that run **directly**: the arguments the client sends are the arguments `execute` receives, with no language model between. Use it for anything a program or a person should call deterministically.

```ts
import { createToolServer, startToolServerHttp, runToolServer, selfAssertedIdentities } from '@backendkit-labs/agent-core';

const options = {
  name: 'ledger',
  version: '1.0.0',
  tools: [balancesTool, payTool],
  agentIdentity: selfAssertedIdentities(),            // who executes the calls
  identity: { userId: 'svc-ledger' },                 // for whom
  // required because payTool is destructive: a direct tool skips the engine's gates
  authorize: async ({ tool, args }) => !tool.destructive || approvals.isValid(args.approvalId as string),
  audit: record => fs.appendFile('tool-calls.ndjson', JSON.stringify(record) + '\n'),
};

await runToolServer(options, { bin: 'ledger-mcp', tokenEnv: 'LEDGER_TOKEN' });   // stdio by default; --http for HTTP
```

What each call gets:

- an **identity check first**: the server needs a digital identity and `identity.userId`, like an agent in the engine, or every call is denied with a reason that says how to fix it; the audit event is attributed to that identity and signed by it;
- validation against the tool's schema **before** anything runs;
- your `authorize` gate or a `policy` (the same contract the engine uses, with `ask` going to an `approver`); one of them is mandatory when a tool is `destructive`, so you cannot forget it;
- a bounded output (default 1 MiB) and an audit record.

`isError: true` always means the call did not run to completion: denied, timed out, threw (the message only, no stack) or returned too much.

**HTTP is closed by default.** Without an auth token the server listens only on loopback, and rejects requests whose `Host` or `Origin` is not loopback (DNS rebinding, cross-site POST).

## Serving an agent

`AgentMCPServer` from `@backendkit-labs/mcp-server` serves an agent's prompt tools and direct tools together. `bk-mcp` serves skills and code intelligence. The flow tools (`createFlowTools`) are plain `ToolDefinition`s, so they can be served the same way: any MCP client gets "start, watch, pause, cancel a flow" with no code of its own.
