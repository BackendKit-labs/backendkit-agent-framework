An agent that can act on real systems needs a layer that is **not** the model deciding what is allowed. In this framework that layer is configuration of the engine: a policy, an approver, an approval store and an audit sink.

## The decision for every call

Before a tool runs, a **policy** answers one of three things:

| Effect | Meaning |
|---|---|
| `allow` | Run it. It can carry a mode: `dry_run` (the tool simulates and writes nothing) or `sandboxed`. |
| `ask` | Someone has to approve first. It can say who may: `accepts: ['human']`. |
| `deny` | Do not run it. The model is told why. |

A policy sees the **principal** (the agent, its delegation chain, the tenant, the user, the roles) and the **call** (the tool with its declared facts, and the arguments).

```ts
import type { ToolPolicy } from '@backendkit-labs/agent-core';

const rules: ToolPolicy = {
  decide(principal, call) {
    if (call.tool.name === 'pay_invoice' && (call.args.amount as number) > 10_000) {
      return { effect: 'ask', reason: 'payment above 10k', accepts: ['human'] };
    }
    return { effect: 'allow' };
  },
};
```

Several policies combine with the rule **deny beats ask beats allow**. A policy that throws denies.

Without a policy of your own, but with someone to ask, the default applies: read-only tools run, destructive tools ask a person, anything that declares nothing asks.

## Who answers an ask

An **approver** answers right away: a person at a terminal (`consoleApprover()`), another agent (`agentApprover(...)`), a UI, a service. Approvals are **checked before they count**:

- its kind must be one the `ask` accepts (an agent cannot satisfy `accepts: ['human']`);
- no agent or service approves a request of its own delegation chain (a person who asked can, unless you turn on [four eyes](#four-eyes-the-person-who-asked-does-not-approve));
- an agent only approves what it could do itself.

### Who may approve: roles

The kind is not enough: "payments over 10k" should be approved by someone in finance, not by any person. Put the role in the `ask`:

```ts
{ effect: 'ask', reason: 'payment above 10k', accepts: ['human'], approverRoles: ['finance'] }
```

The approver needs **at least one** of the roles. The engine does not take them from what the caller says: it asks **your** user system, through an `approverDirectory`.

```ts
createBaseEngine({
  /* ... */
  approverDirectory: {
    async describe(by) {                                   // by = { kind: 'human', id: 'ana' }
      const user = await users.find(by.id);
      return user && { roles: user.roles, tenantId: user.tenantId };   // undefined if you do not know the id
    },
  },
});
```

It fails closed. The approval is refused, and the call does not run, when there is no directory, when it does not know the id, when it throws, when the approver belongs to another tenant than the request, or when none of the roles matches. The audit event of an accepted call records which role covered it (`approval.authority`). This applies to the approver that answers right away and to a stored approval when `runApproved` runs it, with the policy and the directory of that moment.

If several policies ask for roles, the approver needs what all of them ask for (the intersection). If nobody can hold them at once, the call is denied.

`approver: 'finance'` (text) still exists, but it is only a hint for whoever routes the request. The engine checks `approverRoles`.

**The framework does not authenticate anyone.** `by.id` must already be verified by your application (a session, a token, single sign-on) before you call `resolve` or return the approver's answer. Never take it from a request body. The directory says what a verified person may do; it cannot tell whether the id is who it claims to be.

### Four eyes: the person who asked does not approve

A role is not enough when the person who asked for the payment is in finance too. Turn on `forbidSelfApproval`:

```ts
createBaseEngine({
  /* ... */
  identity: { userId: 'carlos', tenantId: 'acme' },   // who the agent acts for
  forbidSelfApproval: true,
});
```

The user the agent acts for (`identity.userId`) cannot approve what it asked for, whatever the kind of approver, and neither can a person in the delegation chain. Another person with the role can. For a stored approval, who asked is what the stored request recorded, so a worker that runs it later with no identity of its own still refuses it.

It is **off by default**, because it changes what is allowed today. It needs `identity.userId`: with none, there is nobody to compare with and the rule does nothing.

## When nobody can answer now: durable approvals

Give the engine an **approval store**. The `ask` is saved as pending, the model is told the call did not run, and whoever decides later (a UI, a CLI, another process) resolves it, and the call runs once:

```ts
const approvals = new FileApprovalStore('./approvals');
const engine = createBaseEngine({ /* ... */ approvals });

await engine.run('pay the October invoices');                  // asks become pending requests

const [req] = await approvals.list({ status: 'pending' });
await approvals.resolve(req.id, { decision: 'approve', by: { kind: 'human', id: 'ana' }, at: new Date().toISOString() });
await engine.runApproved(req.id);                              // runs once; a second call throws
```

`FileApprovalStore` allows exactly one decision and one execution per request, even across processes sharing the directory. `runApproved` repeats every check.

### Approvals that expire

By default a stored request never expires: someone who approved on Monday still authorizes the payment on Friday. To limit that, give the request a lifetime:

```ts
createBaseEngine({ /* ... */ approvals, approvalTtlSeconds: 24 * 3600 });      // for every ask

// or per ask, in the policy; the shorter one wins
{ effect: 'ask', reason: 'payment above 10k', accepts: ['human'], ttlSeconds: 3600 }
```

The request carries `expiresAt`. Once it has passed, `runApproved` refuses the approval whether it was still pending or already approved. The refusal is audited (`deny`, with the time it expired) and the request is spent: a new one has to be made. A `ttlSeconds` that is not a positive number expires at once, and an `expiresAt` that cannot be read counts as expired, so a mistake does not turn into "never expires". An approver that answers right away (`approver`) is not affected: there is no window to wait out.

### What the person sees

An approval is only as good as what it shows. The arguments of the call reach the approver in full (a custom `Approver` receives the whole request). The older `onToolApproval` callback and the `tool_approval_request` event show a preview of up to 4000 characters, and when it is cut they say how much is not shown (`... [1200 more characters NOT shown]`): a long argument cannot push the part that matters out of sight without the person being told. If you build your own approval screen, show the full arguments, or at least the fields the decision depends on.

### An approver that does not answer

Asks are put to the approver one at a time, so one that never answers holds every other ask of the engine behind it. Give it a time limit; past it the call is denied (and audited) and the engine moves on:

```ts
createBaseEngine({ /* ... */ approver, approverTimeoutMs: 5 * 60_000 });
```

Without `approverTimeoutMs` there is no limit. A person on a terminal or a chat may need hours; use [stored approvals](#approvals-that-expire) for that and keep this for approvers that should answer quickly.

## Audit

Each tool call, accepted or refused, produces **one audit event**, with the arguments as a SHA-256 only (no sensitive values in the log). `HashChainAuditSink` writes them chained, so removing or editing a line is detectable.

```ts
createBaseEngine({ /* ... */ audit: new HashChainAuditSink('./audit.log') });
```

Each entry is flushed to disk before the call returns, so a crash of the machine does not lose what was recorded. Where throughput matters more than that, `new HashChainAuditSink(path, { fsync: false })` skips the flush: the last entries may be lost in a crash, and the chain stays valid up to what reached the disk. Leave it on for anything that answers to an auditor.

### Evidence a third party can check

The chain alone only protects you from someone who kept an earlier `head`: a person who can rewrite the whole file can recompute every hash, and a MAC needs the verifier to hold the secret. To let someone **else** check the log, sign checkpoints with an Ed25519 key:

```ts
import { HashChainAuditSink, ed25519Signer, exportAuditBundle, verifyAuditBundle } from '@backendkit-labs/agent-core';

const audit = new HashChainAuditSink('./audit.log', {
  checkpoints: { signer: ed25519Signer(privateKeyPem, 'k1'), path: './checkpoints.ndjson', every: 100 },
});
audit.checkpoint();                       // also on demand: before an export, at the end of the day

exportAuditBundle({ log: './audit.log', checkpoints: './checkpoints.ndjson', publicKeys: { k1: publicKeyPem }, outDir: './bundle' });
```

The auditor, with **only the public key you gave them separately**, checks it offline:

```ts
const result = verifyAuditBundle('./bundle', { trustedKeys: { k1: publicKeyPem } });
// { ok: true, entries, checkpoints, signedUpTo, unsignedTail, keySource: 'verifier', anchored: false, warnings }
```

It checks the chain, each signature, that every checkpoint names a real entry with that hash, and that they go forward. Changing, dropping or reordering anything the checkpoints cover is detected, including a log rewritten whole with every hash recomputed. Keys can rotate: keep the old public keys to verify old checkpoints.

What it does **not** prove, and the result says so:

- **Entries after the last checkpoint** are not covered by any signature (`unsignedTail`). Cutting them off is not detected, unless an anchor covers them (below).
- **Whoever holds the private key can rewrite the log and sign it again.** What stops that is an anchor outside their reach (below). Without one, `anchored` is `false`.
- **The keys in the bundle are not to be trusted.** Without `trustedKeys` the check uses the bundle's own `keys.json` and says `keySource: 'bundle'`: it shows the log is consistent with the key it carries, not who owns it.

#### Anchor the head outside the operator's reach

An anchor records `(seq, head)` somewhere the operator cannot rewrite. From then on, changing any entry up to that point is detected even by whoever holds the signing key and rewrote the log, the checkpoints and the keys.

```ts
import { anchorAuditLog, fileAnchor } from '@backendkit-labs/agent-core';

// Call it when it matters: end of day, before an export. The witness file lives on a host or a volume the operator cannot write.
await anchorAuditLog({ log: './audit.log', anchors: './anchors.ndjson', anchor: fileAnchor('/mnt/witness/heads.ndjson') });
exportAuditBundle({ /* ... */ anchors: './anchors.ndjson', outDir: './bundle' });
```

The auditor checks it with **their own** copy of the witness, never with the path a record claims:

```ts
const result = await verifyAuditBundleAnchored('./bundle', {
  trustedKeys: { k1: publicKeyPem },
  anchors: [fileAnchor('/my/copy/of/heads.ndjson')],
});
// { ok: true, anchored: true, anchoredUpTo: 4200, ... }   or   { ok: false, reason: 'anchor 2 (file) does not verify: ...' }
```

An anchor that does not verify fails the bundle. Records of a kind the auditor did not pass are listed as not verified, and the log is not called anchored. `anchoredUpTo` is how far the anchor covers; entries after it are reported.

What counts is **where the anchor lives**, not this code. A file the operator can edit anchors nothing: it is a record. `fileAnchor` is the simple one. `TimestampAnchor` is an interface (`anchor` and `verify`), so a sealed timestamp (RFC 3161), a commit in a repository the operator does not control, or a service of your own is another implementation of the same thing. None of those is built yet.

So a bundle is **tamper-evident**; with a verified anchor outside the operator's reach it also resists whoever holds the key, up to `anchoredUpTo`. It is the evidence an auditor can evaluate. It is not a legal guarantee, and no standard is claimed to be met.

## Credentials: leased for one call

An agent's `secrets` reach **every tool it calls**, all of them, from the first call to the last. A tool can instead declare the credentials it needs, and the engine leases them from a **broker** only once the call is authorized, for that call only:

```ts
const pay = defineTool({
  name: 'pay_invoice', destructive: true,
  credentials: ['treasury'],                                  // what this tool needs, and nothing else
  /* ... */
  execute: async (args, ctx) => callTreasury(args, ctx.credentials!.treasury),
});

createBaseEngine({
  /* ... */
  credentialBroker: {
    async lease({ name, tool, argsHash, principal, approval }) {
      // YOUR code: ask your vault or your gateway for a credential scoped to this tool and this call.
      const token = await vault.issue({ name, forTool: tool, forCall: argsHash, forUser: principal.userId, ttlSeconds: 60, singleUse: true });
      return { value: token.value, id: token.id, expiresAt: token.expiresAt, release: () => vault.revoke(token.id) };
    },
  },
});
```

The order is the point. The broker is asked **after** the policy, the guardrails and any approval have passed, and it learns which call it is for: the tool, the user, the hash of the arguments (the same one in the audit event) and the approval that authorized it. A call that is denied, or waiting for a person, never reaches it. `release` runs when the call ends, whatever happens: success, error or timeout.

It fails closed. The tool does not run, and the refusal is audited, when no broker is configured, when the broker throws, or when it returns a lease with no value or no id, already expired, or with an expiry that cannot be read. With several credentials it is all or nothing: if the second is refused, the first is given back. A simulation (`dry_run`) writes nothing, so it gets no credentials and never calls the broker.

The audit event keeps `credentials: [{ name, id, expiresAt, released }]`: which lease, never its value. `released: false` means the release failed and the credential may still be valid: look at it.

**What it gives you and what it does not.** It gives a credential scoped to a call, short-lived, revoked afterwards, issued only after authorization and traceable in the audit. It does **not** keep the value away from the tool: the tool receives it in its own process, so a bug in the tool, or a tool that ignores the abort signal after a timeout, can still use or leak it while it is valid. That is why a lease should have an `expiresAt` and `release` should revoke it. If you need the process never to hold the secret, the lease's `value` can be a handle to a proxy outside the process that injects the real secret only on the governed route. That proxy is not part of the SDK: the framework ships the contract (`CredentialBroker`) and the checks around it, not an implementation.

A tool served directly (`createToolServer`) has no engine around it, so it leases nothing: use `credentials` with an engine.

## Why outside the model

A model can be talked into things. A policy cannot. If the rule is "payments over 10k need a human", it lives in `decide`, not in the prompt, and it holds whatever the model says or is told.
