title: "Learning & Self-Improvement"
description: "A closed feedback loop — repeated failures get detected as patterns and automatically promoted into policy rules that prevent recurrence, without a human re-teaching the agent each time."
---

Most of this framework reacts to the current input. This part reacts to *history*: every gate finding gets recorded, repeated findings become a detected pattern, and a pattern above a severity/frequency threshold gets promoted into a `PolicyRule` the [Orchestrator](/concepts/orchestrator) applies automatically on every future run — no one has to notice the pattern by hand and write a rule for it.

<Note>
  This is one of three separate, non-overlapping mechanisms this page covers: the generic **Reflection Engine** (`agent-core`, any agent type), `agent-coding`'s **`LearningRouter`** (free-text "remember this" classification — no thresholds, no patterns), and `agent-enterprise`'s **`EnterpriseReflection`** wrapper (the same core engine, gated behind human approval). Don't confuse them — they solve different problems and none of them replaces another.
</Note>

## The pipeline, in one pass

```
1. CAPTURE    A gate produces a finding (AuditFinding) — or any hook reports one directly
2. ACCUMULATE FailureRecord gets added to a FailureCatalog on disk
3. DETECT     PatternDetector groups by (domain, failureType); ≥3 occurrences = a pattern
4. PROMOTE    high/critical patterns become a ManifestPolicyRule in manifest.yaml
5. ENFORCE    Orchestrator.orchestrate() reads manifest.yaml on every call, merges it
              into policy evaluation — the rule now fires deterministically, no LLM re-judgment
6. LEARN      A lessons-learned memo gets written and can be injected into system prompts
```

Steps 1–4 and 6 are the **Reflection Engine**, documented below. Step 5 is a single line inside the `Orchestrator` you already know from [Orchestrator](/concepts/orchestrator).

## Audits: where findings come from

`AuditReporter` (`packages/core/src/orchestration/audit-reporter.ts`) is the thing that actually produces findings, one gate at a time:

```ts
// AuditReporter lives under the /orchestration subpath, not the top-level export
import { AuditReporter } from '@backendkit-labs/agent-core/orchestration';

auditReporter.recordGate('security', 'security-agent', 'NO-GO', [
  { id: 'F-001', dimension: 'input-validation', hallazgo: 'Endpoint accepts unvalidated SQL parameter',
    severidad: 'critical', evidencia: 'src/routes/search.ts:42', agenteResponsable: 'backend',
    recomendacion: 'Use parameterized queries' },
]);
```

<Note>
  There are two distinct `AuditFinding` interfaces in the codebase — this one (`packages/core/src/orchestration/audit/types.ts`, used by `AuditReporter.recordGate`) requires `id` and `evidencia`; the one `AuditHook.reportFinding` takes (`packages/core/src/reflection/types.ts`) makes both optional. They're not interchangeable — match the one the function you're calling actually expects.
</Note>

Each gate gets a verdict — `'GO' | 'NO-GO' | 'NO-GO condicional'` — and a list of findings if it didn't pass clean. A few things worth knowing about how this stays usable at scale:

- **Silent-gate buffering.** A `GO` gate with zero findings doesn't write its own file — it accumulates in `AuditSilentGatesBuffer` and gets consolidated into one daily report instead of 130 near-empty ones.
- **`generateFinalReport(sprint)`** rolls every gate's verdict into one sprint-level report — `NO-GO` if any gate had a critical finding — and writes a `lessons-learned.md` memo alongside it.
- **`AuditFindingTracer.markResolved(gates, findingId, commitHash)`** lets a later commit close out a specific finding, so unresolved findings (`AuditPendingIssues`) genuinely track what's still open, not what was ever found.

`completeSprint()` is also where the audit system hands off to the Reflection Engine — see the next section.

## The Reflection Engine — the generic core

`ReflectionEngine` (`@backendkit-labs/agent-core`) is domain-agnostic and works the same way regardless of what kind of agent you're building:

```ts
import { ReflectionEngine } from '@backendkit-labs/agent-core';

const engine = new ReflectionEngine({ projectRoot: cwd, appName: 'my-agent' });
await engine.initialize();   // loads the failure catalog from disk — call this before anything else

const { patterns, promotedRules } = await engine.reflect();
```

A `FailureRecord` is the atomic unit — one finding, one occurrence:

```ts
interface FailureRecord {
  id: string; domain: string; failureType: string;
  severity: 'critical' | 'high' | 'medium' | 'low';
  dimension: string; gate: string; agenteResponsable: string;
  hallazgo: string; recomendacion: string; archivos: string[]; fecha: string;
  resolvedByCommit?: string; resolvedAt?: string;
}
```

Five built-in domains ship with the engine — `audit`, `test`, `commit`, `agent`, `bootstrap` — each with its own fixed set of `failureType`s (e.g. `audit`'s includes `hardcoded_secret`, `missing_test_coverage`, `security_vulnerability`; `agent`'s includes `wrong_agent_selected`, `agent_hallucination`, `delegation_failed`). `PatternDetector.scan()` groups every `FailureRecord` by `(domain, failureType)` — a group at or above the threshold (default **3**) becomes a `DetectedPattern`.

<Warning>
  Not every pattern gets auto-promoted, even with `autoPromote: true` (the default). `ReflectionEngine.reflect()` only promotes a pattern when **all** of these hold: severity is `high` or `critical` (never `medium`/`low`), the count is at or above `promotionThreshold`, the failure type doesn't start with `unknown_`, and the project hasn't already hit `maxAutoGeneratedRules` (default **20**). This is a deliberate ceiling — the engine won't silently accumulate an unbounded rule set from noisy or low-severity findings.
</Warning>

A promoted pattern becomes a `ManifestPolicyRule`, written to `~/.{appName}/manifest.yaml` (or a project-local path) by `PolicyPromoter`:

```yaml
# manifest.yaml (excerpt)
policyRules:
  - id: POL-AUDI-001
    name: "Auto-promoted: hardcoded_secret"
    if: { domain: audit, keywords: [secret, hardcoded, credential] }
    then: { requireSecurityReview: true, mustPass: [security-scan] }
    trigger: { domain: audit, pattern: hardcoded_secret, minOccurrences: 3 }
    autoGenerated: true
    createdAt: "2026-06-15T10:00:00.000Z"
    engineVersion: "1.0"
```

## Closing the loop: the Orchestrator reads this automatically

This is the part that makes the whole system a genuine feedback loop rather than a report nobody reads: `Orchestrator.orchestrate()` calls `loadManifest()` on **every** invocation, reading `~/.{appName}/manifest.yaml`'s `policyRules` and merging them with whatever `customRules` you passed at construction — before `evaluatePolicies` runs. Once `hardcoded_secret` has been promoted, every future task touching a keyword like `secret`/`credential` requires a security review automatically, with zero code change and zero LLM judgment call involved in deciding *that* it applies.

## Bootstrapping from history: `HistoricalLoader`

A project doesn't start the Reflection Engine with an empty catalog if it already has a history of NO-GO audit reports on disk. `HistoricalLoader` scans `~/.{appName}/projects/{key}/audits/*.md`, parses each report's findings table, converts each row into a `FailureRecord`, and calls `engine.reflect({ autoPromote: true })` once loaded — so patterns already present in your project's audit history get promoted on the very first run, not three incidents from now:

```ts
// HistoricalLoader isn't in the top-level export — only the /reflection subpath
import { HistoricalLoader } from '@backendkit-labs/agent-core/reflection';

const loader = new HistoricalLoader({ engine });
const result = await loader.loadAll();
console.log(`${result.loaded} findings loaded, ${result.patterns.length} patterns detected`);
```

## Extending it yourself: custom domains

The five built-in domains are audit/dev-workflow flavored — nothing about the engine itself is. `DomainRegistry` lets any agent define its own domain with its own `failureType`s, independent of `agent-coding`:

```ts
import { DomainRegistry, ReflectionEngine } from '@backendkit-labs/agent-core';

const registry = new DomainRegistry({ projectRoot: cwd, appName: 'finance-agent' });
await registry.load();

await registry.registerDomain({
  name: 'compliance',
  description: 'Financial approval and disclosure failures',
  failureTypes: [
    { name: 'over_approval_threshold', severity: 'critical', dimension: 'approval-limits',
      keywords: ['threshold', 'exceeds', 'unauthorized amount'],
      recommendation: 'Require a second approver above the configured threshold' },
  ],
});
await registry.enableDomain('compliance');

const engine = new ReflectionEngine({ projectRoot: cwd, appName: 'finance-agent', registry });
await engine.initialize();

// Report an incident whenever your own gate/hook detects one:
await engine.reportIncident({
  domain: 'compliance', failureType: 'over_approval_threshold', severity: 'critical',
  dimension: 'approval-limits', gate: 'finance-review', agenteResponsable: 'finance-agent',
  hallazgo: 'Approved a $50,000 transfer, exceeds the $10,000 single-approver threshold',
  recomendacion: 'Require a second approver above $10,000', archivos: [], fecha: new Date().toISOString(),
});

await engine.flushReflections();   // detect + promote for domains with pending incidents
```

Three `over_approval_threshold` incidents later, a `compliance` policy rule gets promoted automatically — same pipeline, same `manifest.yaml`, same automatic enforcement, none of it specific to code.

## Coding-specific: free-text learning via `LearningRouter`

This is a **different, simpler mechanism** — not threshold-based, not pattern detection, no `manifest.yaml` involved. It exists only in `agent-coding`, wired to the `save_learning` tool every builtin agent has in `allowedTools`. An agent calls it with a plain sentence; an LLM call classifies it into one of five types and writes it straight to disk, once, immediately:

| Type | Written to | Example |
|---|---|---|
| `tool_quirk` | `agent-notes/{agentId}.md` | "The `docker` CLI here needs `--platform linux/amd64`" |
| `skill` | `skills/{name}.md` | A reusable step-by-step procedure — see [Skills](/concepts/skills) |
| `project` | `memory/contexto-proyecto.md` | "This repo uses Zod for all API validation" |
| `user` | `USER.md` | A preference about how the user likes to work |
| `session` | discarded | Ephemeral, not worth keeping |

```ts
// packages/coding/src/tools/save-learning.ts — what the LLM actually calls
save_learning({ content: "The staging DB requires SSL — connection string needs ?sslmode=require" })
// → classified as tool_quirk, target_agent: 'backend'
// → appended to agent-notes/backend.md (or skips if routeLearning's duplicate check finds it's already there)
```

<Warning>
  There's no promotion, no threshold, no severity gate here — one mention is enough to write a note or generate a skill file. That's the tradeoff: faster to capture, but it doesn't distinguish a one-off remark from a genuine recurring pattern the way the Reflection Engine does. Use `save_learning` for "remember this specific thing"; the Reflection Engine is for "notice when this keeps happening."
</Warning>

## Enterprise-specific: human-gated promotion

`agent-enterprise`'s `EnterpriseReflection` wraps the same core `ReflectionEngine` — it doesn't fork or replace it — with two changes that matter for a business context: **`autoPromote` is always `false`**, and thresholds are per-severity instead of one fixed number (`critical: 1, high: 2, medium: 3, low: 3` — a single critical incident is enough to flag a pattern, nothing needs to repeat three times first).

```ts
import { EnterpriseReflection, recordGateOutcome } from '@backendkit-labs/agent-enterprise';

const reflection = new EnterpriseReflection({ vaultPath, appName: 'bk-enterprise' });
await reflection.initialize();

// A ComplianceGate's outcome becomes incidents — filed under the gate's *executor*,
// never the evaluator, so an agent can't under-report its own failures.
await recordGateOutcome(gateRecord, reflection);

const pending = await reflection.pendingPromotions();   // nothing auto-promotes — a human decides
for (const { pattern } of pending) {                    // PendingPromotion = { pattern, detectedAt }
  await reflection.approvePromotion(pattern, 'compliance-officer@company.com');
  // or: await reflection.rejectPromotion(pattern, approver, 'False positive — expected behavior');
}
```

It also adds a symmetric **demotion** path (`demotionCandidates()`/`approveDemotion()`) for rules whose `outcomes.failure` rate suggests they're doing more harm than good — the core engine has no equivalent; once a rule promotes there, it stays until removed by hand.

## What's generic vs. coding-only vs. enterprise-only

| Piece | Import from | Reusable by any agent? |
|---|---|---|
| `ReflectionEngine`, `DomainRegistry` | `@backendkit-labs/agent-core` (top-level) | Yes — no coding assumptions anywhere |
| `PatternDetector`, `PolicyPromoter`, `HistoricalLoader`, `FailureCatalog`, `AuditHook` and the other hooks | `@backendkit-labs/agent-core/reflection` | Yes — same package, a subpath export, not the top-level one |
| `AuditReporter` and the `audit/*` helpers | `@backendkit-labs/agent-core/orchestration` | Yes — works with any `Orchestrator` |
| `Orchestrator.loadManifest()` auto-enforcement | `@backendkit-labs/agent-core` (top-level) | Yes — automatic the moment `manifest.yaml` exists |
| `LearningRouter`, `save_learning` tool | `@backendkit-labs/agent-coding` | No — coding-agent-specific, writes to skills/agent-notes conventions from [Skills](/concepts/skills) |
| `EnterpriseReflection`, `recordGateOutcome`, `ENTERPRISE_DOMAINS` | `@backendkit-labs/agent-enterprise` | No — built for the 6 department profiles, human-approval workflow specific to business use |
