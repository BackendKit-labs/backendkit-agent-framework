`AgentProfile` is the one type every agent definition in BackendKit conforms to — whether it's one of `agent-coding`'s 10 builtin specialists, one of `agent-enterprise`'s 6 department profiles, or an agent discovered from a remote MCP server.

```ts
interface AgentProfile {
  id: string;
  name: string;
  icon: string;
  description: string;
  systemPrompt: string;
  allowedTools: string[];
  delegatesTo?: string[] | ['*'];
  provider?: string;          // override the engine's default provider for this agent
  model?: string;             // override the model, keep the same provider
  suppressDefaultOutput?: boolean;
  source?: 'builtin' | 'global' | 'project' | 'registry' | 'mcp';
}
```

<Tip>
  `provider`/`model` overrides mean a single engine can run a cheap model for lightweight agents and a stronger one for heavy reasoning — e.g. QA reviewers commonly run on a reasoning-tier model while implementation agents run on a faster one.
</Tip>

## Tool scoping

`allowedTools` is the entire access-control surface for a specialist. A read-only reviewer and a specialist that writes files differ only in which tool names are in this array — there's no separate permission system layered on top.

```ts
const READ_ONLY_TOOLS = ['read_file', 'list_directory', 'search_files'];
const WRITE_TOOLS      = [...READ_ONLY_TOOLS, 'write_file', 'edit_file', 'run_command'];
```

## Where profiles come from

A profile's `id` is the only thing that has to be unique — where it's *defined* varies:

- **Code** — `agent-coding`'s `CODING_AGENTS` array is plain TypeScript.
- **Files on disk** — `loadAgentsFromDir()` reads `~/.{appName}/agents/` (global) and `{cwd}/.{appName}/agents/` (project, git-tracked), with project overriding global overriding builtin. Each agent is either a single `{id}.yaml`/`{id}.json` file or a package directory (`{id}/agent.yaml`) — there's no `.md` companion merged in at load time; `runGlobalSeed` writing a `{id}.md` alongside `{id}.json` is a seeding convenience for humans to edit, not something the loader itself reads back.
- **Remote MCP servers** — `agentDiscovery` on `createBaseEngine` and `MCPClientManager` register MCP-exposed tools as full agents with `source: 'mcp'`.

## Delegation

`delegatesTo` is how one agent hands work to another via the `ask_agent` tool:

```ts
{ id: 'general', delegatesTo: ['*'] }        // can delegate to anyone registered
{ id: 'backend', delegatesTo: ['coder'] }     // can only delegate to `coder`
{ id: 'coder' }                                // no delegatesTo — pure executor, doesn't relay
```

<Note>
  Not every specialist needs to relay through `coder`. The framework's own calibration principle: ceremony should match the size of the task — a one-line fix doesn't need a 4-hop pipeline. Specialists execute directly with their own write tools; `coder` exists for bulk/parallel work, not as a mandatory hop.
</Note>
