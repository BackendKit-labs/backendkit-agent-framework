`Orchestrator` runs before the LLM sees a user's input. It's a deterministic, four-stage pipeline that classifies a task and decides which agents and approval gates apply — so the LLM doesn't have to re-derive that from scratch on every message.

```ts
import { Orchestrator } from '@backendkit-labs/agent-core';

const orchestrator = new Orchestrator({
  client: llmClient,          // only used for intent detection
  capabilityMatrix: MY_CAPABILITY_MATRIX,
});

const engine = createBaseEngine({ ...opts, orchestrator });
```

## The pipeline

1. **Intent detection** — classifies `actionType` (`design`, `implementation`, `test`, `security_audit`, …).
2. **Domain detection** — keyword-matches the input against a domain map to populate `task.domains`.
3. **Risk scoring** — computes `riskLevel` from risk factors (`breaking_change`, `security_sensitive`, `db_transactional`, …).
4. **Policy engine** — evaluates rules against the classified task to decide `mustInclude` agents and required gates.

The result (`OrchestrationResult`) is injected into the default agent's system prompt as a brief: recommended agents in priority order, a suggested execution pipeline, and required gates — the LLM is told to prioritize this, not forced to follow it blindly.

<Note>
  Step 4's rule set isn't only whatever `customRules` you pass at construction — `orchestrate()` also reads `~/.{appName}/manifest.yaml`'s `policyRules` on every call and merges them in automatically. That file is where the [Reflection Engine](/concepts/learning-and-audits) writes auto-promoted rules once a failure pattern repeats — so a gate you never explicitly configured can start firing on its own, once the framework has seen the same kind of finding enough times.
</Note>

## Gates: architecture, security, qa — and beyond

Three built-in review gates ship with sensible defaults, matching `agent-coding`'s roster:

```ts
interface ReviewAgentIds {
  security?: string;      // default: 'security'
  architecture?: string;  // default: 'architecture'
  qa?: string;             // default: 'qa-engineer'
}
```

If your agent roster uses different IDs, override them — this doesn't change any built-in behavior, it just points the same gate logic at different agent names:

```ts
new Orchestrator({
  reviewAgents: { security: 'sec-reviewer', qa: 'code-reviewer' },
});
```

<Warning>
  `DEFAULT_RULES` (the built-in policy rules) assume agent-coding's roster and are **on by default** for backward compatibility. A vertical without a `qa-engineer`/`security`/`architecture` agent should pass `includeDefaultRules: false` and supply its own `customRules`.
</Warning>

### Gates with names you choose

`architecture`/`security`/`qa` aren't the only gates the engine can express. `TaskContext` carries an **open** gate set:

```ts
interface TaskContext {
  // ...
  customGates: Record<string, boolean>;      // e.g. { compliance: true }
  completedCustomGates: string[];            // names already satisfied
}
```

A policy rule can require one by name:

```ts
{
  if: { domain: 'finance' },
  then: { requireCustomGates: ['compliance'] },
}
```

`resolveGates()` builds a pipeline entry for every `customGates` name that isn't yet in `completedCustomGates`, and `resolveCommitAllowed()` blocks on it the same way it blocks on the three built-ins. Custom gates don't get their own FSM state — they're a flat checklist, satisfied from outside the LLM loop entirely (a human approval, a business webhook), not something the engine tries to resolve on its own.

<Tip>
  This is why the gate system didn't need a second orchestrator for non-coding verticals. The FSM's three named review states (`design_review`/`security_review`/`qa_review`) have real ordering semantics worth keeping — architecture before implementation, security before QA. Custom gates don't need that ordering, so they don't need new FSM states either.
</Tip>

## `CapabilityMatrix`: routing by domain

```ts
type CapabilityMatrix = Record<string, {
  owns: string[];       // domains this agent is authoritative for
  skills: string[];
  baseWeight?: number;  // 0.0–1.0, default 0.8
}>;
```

When the domain-detection stage tags a task with a domain, `selectAgents()` checks the matrix for any agent that `owns` it and scores it in. This only works if your domain-detection keywords actually produce the domain names your matrix uses — the built-in domain map is keyword-tuned for coding (`backend`, `frontend`, `security`, `devops`, …), so a non-coding vertical needs its own domain keywords before a `CapabilityMatrix` has anything to match against.

## Single source of truth

`resolveGates()`/`resolveCommitAllowed()` in `gate-resolver.ts` are the only place gate/pipeline logic lives — `Orchestrator.orchestrate()` calls them rather than duplicating the logic inline. If you're extending gate behavior, that's the one file to change.
