Every architecture in the [Quickstart](/getting-started/quickstart) maps to a real template under `packages/templates/base/`. Before walking through them, this page explains the two fields every template leaves you staring at — `allowedTools: []` and `delegatesTo: []` — because nothing below makes sense until those do.

## Building block 1 — Tools

A tool is a typed function, defined with `defineTool`:

```ts
import { defineTool, z } from '@backendkit-labs/agent-core';

export const exampleAction = defineTool({
  name: 'example_action',                              // ← this string is what allowedTools references
  description: 'TODO: describe what this tool does',    // ← the LLM reads this to decide when to call it
  input: z.object({
    target: z.string().describe('Target to act on'),
  }),
  execute: async ({ target }) => {                      // args are already validated against `input`
    return `Action executed on: ${target}`;
  },
});
```

Two names exist for the same thing, and they're not interchangeable: `exampleAction` is the **JS export** you import into `engine.ts` to register it in a `ToolRegistry`. `'example_action'` is the **string name** — the one the LLM sees, and the one `allowedTools` arrays reference. Registering a tool in the engine doesn't give every agent access to it — it just makes it *available*.

## Building block 2 — `allowedTools`

```ts
allowedTools: ['example_action'],
```

This is the actual access-control mechanism, enforced at every tool call — verified directly in the engine's tool-execution path:

```ts
} else if (
    !profile.allowedTools.includes(call.name) &&
    (profile.allowedTools.length > 0 || (profile.delegatesTo && profile.delegatesTo.length > 0))
) {
    result = `Tool "${call.name}" is not authorized for agent "${profile.id}". Use ask_agent to delegate to a specialist.`;
```

If an agent's prompt somehow convinces the LLM to call a tool not in its `allowedTools`, the engine rejects it with exactly that message — this isn't advisory, it's a hard check on every call. That's why the orchestrator template has `allowedTools: []`: it isn't supposed to touch tools directly at all, only delegate.

## Building block 3 — Delegation and `ask_agent`

```ts
delegatesTo: ['specialist-a', 'specialist-b'],
```

Here's the part that surprises people: **`delegatesTo` is not checked against the target agent ID anywhere in the engine.** There's a private method (`resolvesDelegateTo`) that looks like it would do this — it's never called. What actually gates delegation is structural, not a permission list:

- The `ask_agent` tool is auto-injected **only** into the default/orchestrator agent's tool list. Every other agent never receives it, so it structurally can't delegate — regardless of what `delegatesTo` says.
- The list of available agents (the "roster") is injected into the system prompt **only** for the default agent too — other agents' prompts never see it.
- `ask_agent` calls run **concurrently**, up to 6 at once by default (`maxParallelAgents`), so a single orchestrator turn can fan out to several specialists in parallel.

So `delegatesTo: []` on a specialist isn't enforcing anything — it's already impossible for that agent to delegate, because it's not the default agent. `delegatesTo: ['specialist-a', 'specialist-b']` on the orchestrator is **documentation that should match what you write in its system prompt** (`create-bk-agent add specialist` reminds you to keep them in sync) — not a runtime permission check. Write the system prompt to only mention the specialists you actually want called; that prompt text is the real gate today.

## Worked example — filling in the placeholders

The scaffold's `specialist-a`/`specialist-b` are meant to be replaced, not decorated. Here's the multi-agent template turned into a real two-specialist git agent:

```ts
// src/agents/orchestrator.ts
export const ORCHESTRATOR_PROFILE: AgentProfile = {
  id: 'orchestrator', name: 'Orchestrator', icon: '🎯',
  description: 'Routes git requests to the right specialist',
  delegatesTo: ['commit-agent', 'branch-agent'],
  allowedTools: [],
  systemPrompt: `You are the orchestrator for a git assistant.
Your ONLY job is to analyze the request and delegate via ask_agent. Never answer directly.

Available specialists:
- commit-agent: stages files, writes conventional commit messages, commits
- branch-agent: creates/switches/merges branches, resolves simple conflicts`,
};
```

```ts
// src/agents/commit-agent.ts
export const COMMIT_AGENT_PROFILE: AgentProfile = {
  id: 'commit-agent', name: 'Commit Agent', icon: '📝',
  description: 'Stages files and writes conventional commits',
  delegatesTo: [],
  allowedTools: ['git_status', 'git_diff', 'git_add', 'git_commit'],
  systemPrompt: `You are a git commit specialist. Follow conventional commits
(feat/fix/refactor/docs/chore). Always run git_status and git_diff before committing.`,
};
```

`commit-agent`'s `allowedTools` lists real tool names — each needs a matching `defineTool` registered in `engine.ts`, same shape as `exampleAction` above, just calling real `git` commands (via `run_command`-style execution) instead of returning a placeholder string.

## The architectures

<Tip>
  Every example below only shows what's specific to that architecture. Tools, `allowedTools`, and delegation work exactly as described above in all of them.
</Tip>

### Minimal — bare engine, full control

```bash
npx create-bk-agent my-agent   # architecture: Minimal
```

```ts
import { createBaseEngine } from '@backendkit-labs/agent-core';
import type { AgentProfile, LLMProvider } from '@backendkit-labs/agent-core';

const myProvider: LLMProvider = {
  chat: async (_messages, _tools, callbacks) => {
    // TODO: call your LLM API here
    callbacks.onDone({ role: 'assistant', content: 'Hello from my agent!' });
  },
};

const myAgent: AgentProfile = {
  id: 'my-agent', name: 'My Agent', icon: '🤖',
  description: 'TODO: describe your agent',
  allowedTools: [], delegatesTo: [],
  systemPrompt: 'TODO: write your system prompt here.',
};

const engine = createBaseEngine({
  providers: { default: myProvider },
  defaultProvider: 'default',
  agents: [myAgent],
  defaultAgent: 'my-agent',
});

await engine.run(process.argv[2] ?? 'Hello');
```

One agent, zero tools, an `LLMProvider` you implement yourself — even the LLM call is a stub. `allowedTools`/`delegatesTo` are empty here for the simplest possible reason: there's nothing else registered to point them at yet. Use this when you're embedding the engine in something that already exists and everything else would get in the way.

### Single — one agent with tools

Same shape as Minimal, but wired to a real provider (`OpenAICompatibleProvider`), a `ToolRegistry` with `exampleAction`/`exampleQuery` registered, and persistent memory:

```ts
// src/agents/my-agent.ts
export const MY_AGENT_PROFILE: AgentProfile = {
  id: 'my-agent', name: 'My Agent', icon: '🤖',
  allowedTools: ['example_action', 'example_query'],   // ← now non-empty: real tools exist to reference
  delegatesTo: [],                                      // ← still empty: it's the only agent, nothing to delegate to
  systemPrompt: `You are a helpful agent that TODO: <describe your domain>.`,
};
```

```ts
// src/engine.ts (relevant part)
const agents = new AgentRegistry();
agents.register(MY_AGENT_PROFILE);

return new AgentEngine({
  // ...
  defaultAgentId: 'my-agent',
  historyPath: HISTORY,           // conversation persists between runs
  memorySystem: memory,           // 3-tier memory auto-injected each turn
});
```

Best for a focused, single-domain assistant — no delegation, no specialist routing, just one agent with real tools and memory. `defaultAgentId: 'my-agent'` also means this agent gets `ask_agent` — but with nobody else registered, it has nothing to delegate to; that's why `delegatesTo` stays `[]` even though structurally it *could* delegate.

### Multi-agent — orchestrator + specialists

```
src/agents/orchestrator.ts     ← delegatesTo: ['specialist-a', 'specialist-b'], allowedTools: []
src/agents/specialist-a.ts     ← delegatesTo: [], allowedTools: ['example_action']
src/agents/specialist-b.ts
src/engine.ts
```

```ts
// src/engine.ts
const agents = new AgentRegistry();
agents
  .register(ORCHESTRATOR_PROFILE)
  .register(SPECIALIST_A_PROFILE)
  .register(SPECIALIST_B_PROFILE);

return new AgentEngine({
  // ...
  defaultAgentId: 'orchestrator',   // ← only this one gets ask_agent + the roster
  historyPath: HISTORY,
  memorySystem: memory,
});
```

This is the delegation pattern from Building Block 3 above, directly, exactly as scaffolded — rename `specialist-a`/`specialist-b`, add more, keep each specialist's system prompt matching what the orchestrator's prompt says about it. Best for a domain that splits cleanly into a handful of specialties (the git-agent example above).

<Warning>
  For a genuinely open-ended number of specialists, or specialists that need real process isolation and their own model, this in-process pattern isn't what you want — see [`@backendkit-labs/mcp-server`](/packages/mcp-server) instead.
</Warning>

### Coding assistant — 10 agents, zero setup

```ts
import { createCodingEngine, TerminalTransport } from '@backendkit-labs/agent-coding';

const engine = createCodingEngine({
  providers: { [provider]: { apiKey, ...(model ? { model } : {}) } },
  defaultProvider: provider,
  workingDir: process.cwd(),
  appName: 'my-coding-agent',
  transport: new TerminalTransport(),
});
```

No agent files to write — `allowedTools`/`delegatesTo` are already filled in for all 10 builtins (`general` delegates to everyone via `delegatesTo: ['*']`, specialists have real tool tiers like `WRITE_TOOLS`). See [`@backendkit-labs/agent-coding`](/packages/agent-coding) for what's configurable on top of this.

### Autonomous — cron/webhook triggers, no human input

```ts
import { createAutonomousAgent, createMemorySystem } from '@backendkit-labs/agent-core';

const monitorAgent: AgentProfile = {
  id: 'monitor', name: 'Monitor', icon: '👁',
  allowedTools: [], delegatesTo: [],
  systemPrompt: `You are an autonomous monitor agent. TODO: describe what this agent monitors.`,
};

const agent = createAutonomousAgent({
  providers: { [provider]: { apiKey } },
  defaultProvider: provider,
  agents: [monitorAgent],
  defaultAgent: 'monitor',
  goal: 'TODO: describe the agent goal',
  memorySystem: memory,
  triggers: [
    { type: 'schedule', cron: '0 9 * * *', task: 'Run daily check and report findings' },
    { type: 'webhook', path: '/events' },
  ],
  webhookPort: 3000,
});

await agent.start();
```

`createAutonomousAgent` is a different factory from `createBaseEngine` — it owns a trigger scheduler and a webhook listener on top of the engine, and `agent.start()`/`agent.stop()` manage their lifecycle. `allowedTools: []` here just means the scaffold doesn't presume what a monitor needs — add whatever tools the trigger's task actually requires (checking a URL, querying a database) the same way as any other architecture.

### Enterprise — local LLM + RAG over your own docs

```ts
import { OllamaProvider } from '@backendkit-labs/agent-coding';
import { ObsidianRAGProvider, VaultWriter } from '@backendkit-labs/agent-enterprise';

const rag = new ObsidianRAGProvider({ vaultPath: config.vaultPath, ollamaHost, embeddingModel });
const writer = new VaultWriter({ vaultPath: config.vaultPath });

const tools = new ToolRegistry();
tools.register(rag.createTool())               // registers as 'search_knowledge'
     .register(writer.createTool('specialist')); // registers as 'write_knowledge'
```

```ts
// src/agents/domain-specialist.ts
export const DOMAIN_SPECIALIST_PROFILE: AgentProfile = {
  id: 'domain-specialist', name: 'Domain Specialist', icon: '📚',
  allowedTools: ['search_knowledge', 'write_knowledge'],   // ← matches the two tools registered above
  delegatesTo: [],
  systemPrompt: `You are a specialist with access to the company's knowledge base.
Use search_knowledge to find information. Never make up information that isn't in the documentation.
When you learn something useful, use write_knowledge to persist it.

// TODO: customize this prompt for your specific domain:
// - HR agent: focus on policies, onboarding, benefits
// - IT support: focus on troubleshooting guides, procedures
// - Sales: focus on product catalog, pricing, FAQs`,
};
```

This is the closest scaffold to `@backendkit-labs/agent-enterprise`'s 6-department pattern, minus the multi-department vault routing — start here for one department, see [`agent-enterprise`](/packages/agent-enterprise) when you need several sharing one vault.

### Orchestrator — a full vertical, pre-built

```bash
npx create-bk-agent my-agent   # architecture: Orchestrator
# workflow template: ventas | marketing | soporte | blank
```

This is the one worth reading in full if you're building anything with several specialists and a real approval process — `ventas` (sales) is a complete `orchestrator.yaml` with six specialists, two multi-step flows, a knowledge vault, and real approval gates:

```yaml
agents:
  - id: proposal-agent
    domain: ventas
    gate: true
    gate_criteria:
      - "El alcance está definido con entregables concretos y medibles"
      - "El pricing propuesto está dentro de la política de descuentos vigente"

  - id: legal-sales-agent
    domain: legal
    gate: true
    gate_criteria:
      - "Las cláusulas de responsabilidad están limitadas al monto del contrato"
      - "El contrato incluye NDA o cláusula de confidencialidad explícita"
```

`marketing` and `soporte` are the same depth. `blank` gives you the skeleton with none of it filled in. This architecture doesn't use `allowedTools`/`delegatesTo` at all — it's config-driven YAML, not `AgentProfile` code; a specialist's capabilities come from its `capabilities: [...]` list and `soul_file` instead.

### Tool-only agent — no LLM at all

Not a `create-bk-agent` choice — for when a tool call is pure deterministic logic with no reasoning step (a health check, a wrapper around another API), none of the above fit. `allowedTools`/`delegatesTo`/`AgentProfile` don't apply here at all, because there's no `AgentEngine`:

```bash
npm install @backendkit-labs/agent-core @modelcontextprotocol/sdk zod dotenv
```

```ts
// src/server.ts
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';

const server = new McpServer({ name: 'my-mcp-server', version: '0.1.0' });

const inputSchema = z.object({ query: z.string().describe('The query to process') });

// @ts-expect-error: MCP SDK + zod generic depth limit, safe at runtime
server.tool(
    'example_query',
    'TODO: describe what this tool does',
    inputSchema.shape,
    async ({ query }: z.infer<typeof inputSchema>) => ({
        content: [{ type: 'text' as const, text: `Result for: ${query}` }],
    }),
);

await server.connect(new StdioServerTransport());
```

If the logic behind a tool call ever needs to reason (read a file and decide what it means, not just return raw output), that's the signal to move to [`@backendkit-labs/mcp-server`](/packages/mcp-server)'s `AgentMCPServer` instead — same MCP surface, but each tool call runs through a real `AgentEngine`.

<Warning>
  `packages/templates/` also has top-level `autonomous/`, `coding/`, `minimal/`, and `domain-agent/` directories outside `base/`. `scaffold.ts` only ever reads from `base/` — those are orphaned, diverged copies, not alternate outputs. If you're editing a template to change what gets generated, `base/` is the one that matters.
</Warning>
