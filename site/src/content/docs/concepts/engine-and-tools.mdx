## One tool, two ways to run it

A tool is a plain definition (`defineTool`). **Who decides to call it** is a separate choice, and the framework supports both:

- **LLM-controlled.** The model decides whether to call the tool, when, and with what arguments. Flexible, but not predictable: the same request can lead to different calls.
- **Deterministic.** Your code or an MCP client calls the tool with exact arguments. No model is involved, so the same input always runs the same call.

<ToolPaths />

| | LLM-controlled (through the model) | Deterministic (direct, no model) |
|---|---|---|
| Who calls it | The engine, because the model asked | Your code, or an MCP client, with exact arguments |
| Arguments | Written by the model | Sent by the caller |
| Result | Goes back to the model, which decides what next | Goes back to the caller as is |
| Safety | The engine's gates: allowed tools, guardrails, [policy](../governance/), approval | Your `authorize` function or a `policy`, one of them required for destructive tools, plus audit |
| Use it for | Open-ended work: understanding a request, choosing steps | Anything a program or a person must call the same way every time |

The same tool serves both. You write it once, declare `readOnly` or `destructive` once, and choose per use. A model can also reach a direct tool: serve it over MCP and an engine with an MCP client sees it next to its own tools ([MCP](../mcp/)).

### Example: LLM-controlled

The tool is `get_weather` from [your first agent](../../start/first-agent/). You give it to an engine and ask a question in plain language. **The model** chooses to call it, and chooses the arguments.

```ts
const result = await engine.run('Do I need an umbrella in London?');

// The model decided to call get_weather, with { city: 'London' }.
console.log(result.toolCalls.map(c => `${c.name}:${c.success}`));   // [ 'get_weather:true' ]
```

Ask the same thing another way and the model may call it twice, or not at all. That freedom is the point, and the reason the engine checks every call before it runs.

### Example: deterministic

The same `weather` tool, with no engine and no model. There are two ways to call it, and the first needs nothing but the framework.

**1. From your own code, in the same process.** `createToolContext` builds the context a tool needs outside an engine (tests, scripts, cron jobs):

```ts
import { createToolContext } from '@backendkit-labs/agent-core';
import { weather } from './tool';

const out = await weather.execute({ city: 'London' }, createToolContext());
// "Weather in London: sunny, 22 C". Always this call, with these arguments.
// A wrong argument ({ city: 42 }) throws ToolArgumentError before `execute` runs.
```

This is a plain function call: the schema is checked, and **nothing else**. There is no policy, no approval and no audit, because those belong to the engine and to the tool server. Use it for tools you trust the caller of, such as a read-only lookup.

**2. From another process or service, over MCP.** Serve the tool, and any MCP client can call it:

```ts
// weather-server.ts
import { runToolServer } from '@backendkit-labs/agent-core';
import { weather } from './tool';

await runToolServer({ name: 'weather', tools: [weather] }, { bin: 'weather-mcp' });   // stdio by default
```

```ts
// any MCP client: a script, a job, another service. This one is the MCP SDK client.
import { Client } from '@modelcontextprotocol/sdk/client/index.js';
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js';

const client = new Client({ name: 'ops-script', version: '1.0.0' });
await client.connect(new StdioClientTransport({ command: 'npx', args: ['tsx', 'weather-server.ts'] }));

const out = await client.callTool({ name: 'get_weather', arguments: { city: 'London' } });
// Always this call, with these arguments. The schema validates them before `execute` runs.
```

The framework has its own client too: `MCPClientManager` turns each tool of a server into a `ToolDefinition`, which you call like the in-process one. The name carries the server as a prefix (`mcp__<server>__<tool>`):

```ts
import { MCPClientManager, createToolContext, MCP_TOOL_ERROR } from '@backendkit-labs/agent-core';

const mcp = new MCPClientManager([{ name: 'weather', transport: 'stdio', command: 'npx', args: ['tsx', 'weather-server.ts'] }]);
await mcp.initialize();

const tool = mcp.getTools().find(t => t.name === 'mcp__weather__get_weather')!;
const out = await tool.execute({ city: 'London' }, createToolContext());   // "Weather in London: sunny, 22 C"
// If the server answers isError: true (bad arguments, denied, it threw), this throws a ToolError with code MCP_TOOL_ERROR.
await mcp.disconnect();
```

`get_weather` is `readOnly`, so the server needs no gate. A `destructive` tool would not start without an `authorize` function or a `policy`, and that is where the gates apply to a direct call: [serving tools directly](../mcp/#as-a-server-without-a-model) shows one.

The rest of this page is the first case: the model-driven loop.

## A turn

`engine.run(question)` runs a loop until the model answers without asking for a tool, or until `maxIterations`:

1. Send the conversation and the tools the agent may use to the model.
2. If the model asks for tools, check each call (allowed tools, argument guardrails, [policy](../governance/)), run it, add the result to the conversation, go to 1.
3. Otherwise the answer is final.

What comes back is a `RunResult`:

| Field | Meaning |
|---|---|
| `text` | What the agent said at the end. |
| `toolCalls` | Every tool call of the turn, in order: `name`, `success`, `errorCode`, a `preview` of the result. |
| `errors` | The messages of the error events of the turn. |
| `aborted`, `budgetExceeded` | The turn was stopped by the caller or by a cost budget. |

Assert on `toolCalls`, not on the model's words. A model can say "Order placed" without placing anything; `toolCalls` says what happened.

## Tools

```ts
import { defineTool, z } from '@backendkit-labs/agent-core';

const readFile = defineTool({
  name: 'read_file',
  description: 'Read a text file inside the project',
  readOnly: true,
  input: z.object({ path: z.string().describe('Path relative to the project') }),
  execute: async ({ path }, ctx) => { /* ... */ return '...'; },
});
```

- The **schema** validates the arguments before `execute` runs. A wrong call from the model becomes an error the model can read and correct.
- The **description** and each `.describe()` are the only documentation the model has. Write them for the model.
- `execute` returns a **string**. Return JSON with `JSON.stringify` when the model needs structure.
- `ctx` carries the abort signal, the agent id, the session and who is acting. Pass `ctx.signal` to anything cancellable (`fetch`, a child process) so a stopped turn stops the work.
- A thrown error reaches the model as a message, not as a crash. Throw a `ToolError` to give it a code and a hint.

### A write that is safe to repeat

A model can ask for the same call twice (after a timeout, after an error it misread). A tool that writes should not apply it twice. The engine gives each call a stable key in `ctx.idempotencyKey`: the same run, agent, tool and arguments always get the same key, and a call resumed from a stored approval carries the approval's id. Pass it to the system you write to:

```ts
const pay = defineTool({
  name: 'pay_invoice',
  description: 'Pay an invoice',
  destructive: true,
  input: z.object({ invoiceId: z.string(), amount: z.number() }),
  execute: async ({ invoiceId, amount }, ctx) => {
    // the payment API applies a request with a key it has already seen once, and returns the first result again
    const res = await fetch('https://treasury.example.com/payments', {
      method: 'POST',
      headers: { 'Idempotency-Key': ctx.idempotencyKey!, 'Content-Type': 'application/json' },
      body: JSON.stringify({ invoiceId, amount }),
      signal: ctx.signal,
    });
    return await res.text();
  },
});
```

Different arguments or another run give another key, so two real purchases of the same item in two runs stay two purchases. The key does not stop a repeat by itself: it is the system you write to that has to honour it.

### Declared facts

| Flag | Says | The engine does |
|---|---|---|
| `readOnly: true` | Changes nothing. | Runs it without asking. Implies safe to run in parallel with other read-only tools. |
| `destructive: true` | Cannot be undone (pay, delete, send). | Asks a person, always. Cannot be combined with `readOnly`. |
| `idempotent: true` | Calling twice is the same as once. | Safe to retry. |

A tool that declares nothing is treated as "may change things": it asks. This is deliberate: forgetting a fact asks too much, never too little.

### Many tools: let the model search

Forty tool definitions cost tokens on every call, and most turns use two. Mark a tool `defer: true`, or list patterns in the agent's `deferTools` (`'crm_*'`, wildcards only), and the model no longer receives its schema. It receives `tool_search` instead, finds a tool by name or description, and from that step on the tool is in its list.

```ts
const sales = {
  id: 'sales', /* ... */
  allowedTools: ['read_file', 'crm_find_contact', 'crm_find_deal' /* ... */],
  deferTools: ['crm_*'],
};
```

- The list only grows, and at the end. Each search still changes the tool list, and the provider's prompt cache stops at the first change, so the history after that point is billed again for that step. Measured with DeepSeek (40 tools, about 2,800 tokens): input tokens fell 45% to 88%, but with cached tokens at a tenth of the price the cost was lower in two of three tasks and higher in one. The gain is certain when the tool list is large (hundreds of tools, MCP servers) or the context window is the limit; with a few dozen tools and a cache, measure first.
- What was found lasts for one run. The next run starts from the short list.
- **Finding authorizes nothing.** The search only looks among tools the agent may already call. A tool that a policy or the sandbox denies is not offered, and calling a deferred tool before finding it fails without running. Approval still applies.
- The default search scores words in the name (more weight) and the description, and returns up to 5 tools. To use your own, for example embeddings, pass `toolSearch`:

```ts
createBaseEngine({
  agentIdentity: selfAssertedIdentities(),   // who the agent is (SPEC-0044)
  identity: { userId: 'me' },                // on whose behalf it acts
  /* ... */
  toolSearch: {
    maxResults: 3,
    search: async (query, candidates) => rankWithEmbeddings(query, candidates), // candidates are already the allowed ones
  },
});
```

A search of your own can only return tools from `candidates`; anything else it returns is dropped.

To stop searches from changing the tool list (and so from cutting the cache), use `toolSearch: { mode: 'message' }`. The list stays fixed; the answer of `tool_search` carries the name, description and parameters of what it found, and the model calls it by name. With DeepSeek (40 tools, 9 runs per variant) it cost the same as listing all 40 tools, 64% fewer input tokens, and no failures; the default `list` mode cost 10% more. It needs a provider that lets the model call a name that is not in the list, so test yours first. Anthropic and OpenAI are not tested.

A model that is weak at tool use may not search. Check with your model before deferring tools it needs on most turns, and leave those out of `deferTools`.

## Agents

An `AgentProfile` is an identity and a list: `id`, `name`, `systemPrompt`, and `allowedTools`, the names of the tools this agent may call. A tool that is registered but not in `allowedTools` is invisible to that agent. With several agents, `delegatesTo` says which others it may ask for help ([multi-agent](../multi-agent/)).

## Putting it together

`createBaseEngine` takes the providers, the agents, the tools and a transport, and builds the engine:

```ts
const engine = createBaseEngine({
  agentIdentity: selfAssertedIdentities(),   // who the agent is (SPEC-0044)
  identity: { userId: 'me' },                // on whose behalf it acts
  providers: { main: provider }, defaultProvider: 'main',
  agents: [assistant], defaultAgent: 'assistant',
  tools: [readFile], transport,
  workingDir: process.cwd(),
  iterationMode: 'auto',     // run until the model is done
  maxIterations: 24,         // but never forever
  maxParallelTools: 4,       // read-only calls of one turn may run together
});
```

`maxParallelTools` above 1 lets the model's read-only calls of a single turn run at the same time. Calls that are not read-only always run one after another.

The transport receives the events of the turn (text, tool calls, results, errors). `StdoutTransport` prints, `CallbackTransport` calls your function, and the testkit's `mockTransport` records them for assertions.
