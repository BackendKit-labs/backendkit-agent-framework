title: "Skills"
description: "Trigger-gated knowledge injection from .md files with frontmatter — one mechanism, two real usages: stack-scoped dev conventions, or domain knowledge for any other agent."
---

Skills are reusable chunks of knowledge injected into an agent's system prompt — but only when they're actually relevant to the current input. Nothing loads a skill "just in case." The mechanism lives in `agent-core` and is agent-agnostic, but it's used differently depending on what kind of agent you're building.

<Warning>
  Today, in practice, only `agent-coding`'s `createCodingEngine` actually wires this system — `agent-enterprise` and every `create-bk-agent` template pass nothing to `createBaseEngine`'s `skills`/`detectedStack`/`loadSkills` options. The mechanism is generic and available to any engine; nothing built on top of it *besides* `agent-coding` uses it yet. Both usages below are real code paths — one is exercised today, the other you'd wire yourself.
</Warning>

## Activation: trigger gate, plus an optional stack gate

```ts
class SkillActivator {
  activate(input: string, skills: Skill[], detectedStack: string[] = []): Skill[] {
    // 1. Stack gate — only applies if skill.language is set; skip if it doesn't match
    // 2. Trigger gate — at least one of skill.triggers must appear in the input
  }
}
```

The stack gate is conditional: a skill with no `language` field skips it entirely and only has to pass the trigger gate. This is the fork in the road between the two usages below.

## Usage 1 — coding agents: stack-scoped dev conventions

This is what `agent-coding` does. Every skill is tagged with `language`, and `detectProjectStack(cwd)` tells the activator which languages the current project actually uses — so a Go project never sees an npm-specific skill, even if it's loaded:

```markdown
---
name: npm-workspaces
version: 1.0.0
description: How to run scripts in an npm workspaces monorepo
language: [node]
triggers:
  - workspace
  - monorepo
  - npm workspaces
---

This project uses npm workspaces. Run scripts with
`npm run <script> --workspace=<name>` from the root, not inside the package dir.
```

The body after the closing `---` becomes `systemPromptAddition` automatically — no separate field needed unless you want the frontmatter to override it.

`createCodingEngine` ships 4 pre-built language packs this way (Node, Python, Go, Java/Kotlin) — each pack is a set of skills scoped to `language: [that stack]`, covering the tooling conventions for that ecosystem (`npm`/`jest`/`tsc` for Node, `pytest`/`ruff`/`mypy` for Python, and so on). Use this pattern when the knowledge genuinely only applies to projects written in a specific language — a skill about Django migrations has no business firing on a Go project.

## Usage 2 — any other agent: domain knowledge, no stack concept

For a sales agent, a support agent, an HR agent — there's no "project stack" to detect at all. The fix isn't a different API, it's simpler: **don't set `language`** on the skill, and don't bother calling `detectStack()`. Every skill you write passes the stack gate automatically (it's skipped whenever `language` is unset) — activation becomes pure trigger matching.

```markdown
---
name: pricing-objection
version: 1.0.0
description: How to respond when a prospect raises a price objection
triggers:
  - too expensive
  - can't afford
  - budget
  - cheaper option
---

When a prospect raises a price objection, don't discount immediately. Reframe around
value delivered vs. cost of inaction first. Only mention flexible payment terms if
they push back a second time.
```

Wire it the same way `agent-coding` does, just without a stack:

```ts
createBaseEngine({
  // ...
  skills: [pricingObjectionSkill, /* ... */],
  // detectedStack intentionally omitted — nothing here needs it
});
```

This is the same `SkillActivator`, the same `SkillLoader` 4-layer hierarchy, the same `SkillManager` installer described below — just used for business/domain knowledge instead of dev tooling.

## Where skills load from: a 4-layer hierarchy

`SkillLoader.loadAll(cwd, projectDir)` reads from four locations, in ascending precedence (later overrides earlier on a name collision):

```
~/.{appName}/skills/global/           ← always loaded, regardless of stack
~/.{appName}/skills/packs/{pack}/     ← installed packs — stack-scoped for coding, or not, for anything else
~/.{appName}/projects/{key}/skills/   ← auto-generated by LearningRouter — NOT git-tracked
{cwd}/.{appName}/skills/              ← project-specific — git-tracked, shared with the team
```

<Warning>
  Only the first two layers are genuinely generic. `SkillLoader`'s *mechanism* for the last two — read a directory, parse what's there — works for any `appName`, but what actually populates or makes sense of them is coding-specific:

  - **`projects/{key}/skills/`** is written exclusively by `LearningRouter` (`packages/coding`) — nothing else in the framework ever writes there. For any agent that doesn't use `agent-coding`, this directory is just permanently empty unless you build your own auto-generation on top of it.
  - **`{cwd}/.{appName}/skills/`** assumes the agent's behavior should vary by which directory it's invoked from — true for a coding agent (different repos are different projects), meaningless for most other agents (a finance-agent isn't "invoked from" a working directory; it's a standing service). Skip `cwd` when calling `loadAll()` and this layer resolves to `[]` automatically, no special-casing needed.

  In practice: a non-coding agent almost always only cares about `global` and `packs`.
</Warning>

<Note>
  **`.md` with frontmatter is the real format — `.yaml`/`.yml` still parses, but is legacy.** Every skill file that actually ships in this codebase today (the coding-agent language packs, the specialist skills in `bk-coder-v2`) is `.md`. Some consumers only look for `.md` at all and never check for `.yaml`. Write new skills as `.md`; treat YAML support as compatibility for anything old, not a format choice for new files.
</Note>

### Who creates these directories

`SkillLoader` itself never creates anything — every `load*` method just tries to read, and returns `[]` if the directory doesn't exist. The actual directory tree, plus `config.json`, `USER.md`, `AGENT.md`, and starter builtin skill files written to disk as real `.md` files, comes from a separate function:

```ts
import { runGlobalSeed } from '@backendkit-labs/agent-core';

await runGlobalSeed(appName, cwd, {
  agents: myBuiltinAgents,   // seeded as {id}.json + {id}.md pairs
  skills: myBuiltinSkills,   // seeded as .md files under skills/global or skills/packs/{pack}
});
```

It's idempotent (safe to call on every startup — only writes what's missing) and creates the whole tree in one pass:

```
~/.{appName}/
├── config.json, USER.md, workspaces.json
├── agent-notes/
├── agents/              ← seeded from options.agents
├── skills/
│   ├── sources.json      ← registry of installed packs
│   ├── global/           ← seeded from options.skills (scope: 'global')
│   └── packs/{pack}/     ← seeded from options.skills (scope: 'pack')
└── projects/{cwd-slug}/
    ├── memory/
    ├── audits/
    ├── skills/            ← empty at seed time — LearningRouter writes here later
    └── checkpoints/
```

`runGlobalSeed` lives in `agent-core` and takes no coding-specific arguments — it's generic. But **only `createCodingEngine` actually calls it today**, fire-and-forget, on every construction. Nothing else in the codebase does.

### For a non-coding agent — where do *your* skills actually live?

Be honest with yourself about what `appName` is first: it's not a generic framework concept, it's a naming convention that `SkillLoader`/`runGlobalSeed`/`ProjectStore` happen to accept as a parameter — and every real usage of it in this codebase today is `agent-coding`. Nothing stops you from passing any string, but you're the one giving it meaning, not the framework.

**No location at all — the common case.** `Skill` is a plain object; nothing about it requires a file on disk:

```ts
const cashflowAnomalySkill: Skill = {
  name: 'cashflow-anomaly', version: '1.0.0',
  description: 'How to flag and explain unusual cash flow patterns',
  triggers: ['anomal', 'unusual', 'flag', 'unexpected'],
  systemPromptAddition: `When flagging a cash flow anomaly, compare against the trailing
  90-day average before calling something unusual, and always state the comparison baseline.`,
};

createBaseEngine({
  // ...
  skills: [cashflowAnomalySkill],   // defined in code, done — no directory, no appName, no loader
});
```

This is exactly how `agent-coding`'s own builtin skill packs are defined — TypeScript constants, not files, loaded straight into the `skills` array. Reach for this first; only add the file-based layer below if you specifically want skills to be editable or installable without a code change.

### Worked example — `finance-agent`, skills and memory together

Say you're building `finance-agent` and you *do* want file-based skills, plus memory that lives alongside them the way `agent-coding`'s does. Nothing wires this relationship for you — `createMemorySystem` takes raw file paths, it has never heard of `appName` — so you compose both yourself, consistently:

```ts
import * as path from 'path';
import * as os from 'os';
import { SkillLoader, runGlobalSeed, createMemorySystem, createBaseEngine } from '@backendkit-labs/agent-core';

const appName = 'finance-agent';                                    // your own choice
const home    = path.join(os.homedir(), `.${appName}`);             // ~/.finance-agent/

// Skills — global + packs only. finance-agent has no notion of "cwd" as a
// project, so loadAll() is called with no cwd/projectDir — the project and
// projectConfig layers just resolve to [] and are left out below.
await runGlobalSeed(appName, cwd, { skills: [cashflowAnomalySkill] });
const loaded = await new SkillLoader(appName).loadAll();

// Memory — you build this path yourself; nothing derives it from appName automatically
const memory = createMemorySystem({
  episodic:   { provider: 'json', path: path.join(home, 'memory', 'episodes.json') },
  semantic:   { provider: 'json', path: path.join(home, 'memory', 'knowledge.json') },
  procedural: { provider: 'json', path: path.join(home, 'memory', 'patterns.json') },
});

createBaseEngine({
  // ...
  skills: [...loaded.global, ...loaded.packs],
  memorySystem: memory,
});
```

Both now sit under the same `~/.finance-agent/` root — `skills/` and `memory/` as real siblings — because you put them there, using the same string for both, the same way `agent-coding` does internally.

<Tip>
  Prefer not to invent your own home directory? [`@backendkit-labs/infra`](/packages/infra)'s `bkPaths.data('finance-agent')` gives you a component-scoped directory under the shared `BK_HOME` (`~/.backendkit/data/finance-agent/`) instead of a one-off `~/.finance-agent/` — use that as your `home` above if you want to participate in the platform-wide home convention rather than inventing a new one. Either way, the composition step (deciding that skills and memory both live under the same root) is still yours to do.
</Tip>

Skip any of this and it degrades gracefully — `SkillLoader.loadAll()` on a directory that doesn't exist just returns `[]` for that layer, same as any other missing directory.

### Skills and memory, side by side — only for coding, today

For `agent-coding` specifically, `~/.{appName}/projects/{key}/skills/` and `~/.{appName}/projects/{key}/memory/` really are siblings under the same root — verified directly: `ProjectStore`'s constructor computes `projectDir` as `join(homedir(), '.{appName}', 'projects', cwdToProjectKey(cwd))`, the exact same path `runGlobalSeed` derives, and `createCodingEngine` points [`createMemorySystem`](/concepts/memory)'s three JSON files at `{projectDir}/memory/*.json`.

<Warning>
  Nobody else follows this convention. `packages/templates/base/{multi-agent,single,autonomous}` hardcode memory at `~/.my-agent/memory/` — a fixed string, not derived from `appName` at all. `agent-enterprise`'s `createEnterpriseSetup` puts memory at `~/.bk-agent/sessions/{sessionId}/` — keyed by session, not project, under yet another hardcoded name. Neither wires skills, so there's no sibling `skills/` directory to speak of for either. If you want skills and memory to share a root the way `agent-coding` does, that's a convention you'd adopt yourself (call `runGlobalSeed`, then point `createMemorySystem` at `{projectDir}/memory/`) — the framework doesn't enforce or default to it outside `agent-coding`.
</Warning>

## In a multi-agent roster: shared by default, not per-agent

`skills` and `memorySystem` are options on `createBaseEngine` itself — **one array, one store, for the whole engine** — not something you configure per `AgentProfile`. That has a concrete consequence once your roster has more than one agent (a default/orchestrator agent plus specialists reachable via `ask_agent`, or `agent-coding`'s 10 builtin agents):

```ts
createBaseEngine({
  agents: [orchestratorProfile, billingSpecialist, complianceSpecialist],
  skills: [cashflowAnomalySkill],       // ← visible to ALL three agents, not just one
  memorySystem: memory,                 // ← same store, same context block, for ALL three
  defaultAgent: 'orchestrator',
});
```

Verified directly in `AgentEngine.buildSystemPrompt(profile)` (`packages/core/src/engine/AgentEngine.ts`): the active-skill addition and the memory context block are computed **once per top-level `run()` call**, from the raw input text, then injected into *every* profile's system prompt unconditionally — the orchestrator, and any specialist it delegates to via `ask_agent`, all see the same skill matches and the same memory recall for that turn. There's no per-agent filtering; nothing here checks which agent is currently active before deciding what to inject.

<Warning>
  This means a skill or memory doesn't "belong" to the specialist it's most relevant to — it's visible engine-wide the moment its trigger matches, regardless of which agent ends up handling the input. If you write a `hr-policy` skill and a `sales-pitch` skill into the same `skills` array, both are candidates for activation on every turn, for every agent in the roster. Keep triggers specific enough not to collide, or split genuinely unrelated domains into separate `AgentEngine` instances rather than one roster.
</Warning>

The one thing that **is** genuinely per-agent — keyed by `agentId`, not shared — is `agent-coding`'s `agent-notes/{agentId}.md`, exposed via `ProjectStore.getAgentNotes(agentId)` and injected only into that specific agent's own prompt (`AgentEngine.ts` reads `this.opts.store?.getAgentNotes?.(profile.id)` per profile, right alongside the shared memory/skill injection). It's a separate mechanism from `skills`/`memorySystem` — tool quirks and per-agent learnings routed there by `LearningRouter`, not general knowledge or history — and, like the rest of `ProjectStore`, it's `agent-coding`-only. Nothing wires an equivalent per-agent note store for other packages; you'd build your own (e.g. a `Map<agentId, string>` you inject into each specialist's `systemPrompt` at registration time) if you wanted the same isolation elsewhere.

## A custom path — for one agent, or a group of them, sharing a route

Everything above uses `~/.{appName}/`, `SkillLoader`'s built-in convention — rigid, HOME-relative, derived from a single string. That's `agent-coding`'s convention; nothing forces it on anyone else. If it doesn't fit — you want a path that isn't under the user's home directory at all, e.g. a shared team folder, a mounted volume, or one directory intentionally reused by several *different* engines/agents — `SkillLoader` isn't the tool for that. `createBaseEngine`'s `loadSkills` option is:

```ts
loadSkills?: () => Promise<Skill[]>;   // packages/core/src/engine/createBaseEngine.ts
```

It's a bare callback — no `appName`, no derived path, no assumption at all about where the files live. Point it at anything, and reuse the same `.md`-frontmatter parser `SkillLoader` uses internally (`parseMdSkill` is exported from `agent-core` for exactly this):

```ts
import { createBaseEngine, parseMdSkill } from '@backendkit-labs/agent-core';
import * as fs from 'fs/promises';
import * as path from 'path';

const sharedSkillsDir = '/mnt/team-shared/finance-and-billing/skills';   // any path you want

async function loadSharedSkills() {
  const files = await fs.readdir(sharedSkillsDir);
  const skills = [];
  for (const file of files.filter(f => f.endsWith('.md'))) {
    const skill = parseMdSkill(await fs.readFile(path.join(sharedSkillsDir, file), 'utf-8'));
    if (skill) skills.push(skill);
  }
  return skills;
}

// finance-agent's engine
createBaseEngine({ agents: [...], loadSkills: loadSharedSkills, memorySystem: financeMemory });

// billing-agent's engine — same directory, same function → same skills
createBaseEngine({ agents: [...], loadSkills: loadSharedSkills, memorySystem: financeMemory });
```

The same applies to memory, only more directly — `createMemorySystem` already takes raw file paths with no `appName` involved at all (see [Memory](/concepts/memory)), so pointing two separate engines at the same `episodic`/`semantic`/`procedural` file paths is enough to have them share a memory root; there's no loader layer to route around in the first place.

Recall from the section above that within *one* engine, every agent in the roster already shares `skills`/`memorySystem` automatically — so "a group of agents sharing a route" is either: agents in the same engine (free, by construction), or agents in separate engines pointed at the same custom path via `loadSkills`/`createMemorySystem` (what this section shows).

## Installing skill packs

`SkillManager` installs skill packs the way a package manager installs dependencies — from a GitHub repo, a local path, an Obsidian vault, or the `skills.sh` registry. This works identically for either usage — a "packs/finance" of trigger-only business skills installs exactly like "packs/node":

```ts
import { createSkillManager } from '@backendkit-labs/agent-core';

const manager = createSkillManager('bk-agent');

await manager.install('github:my-org/my-skill-pack');
await manager.list();               // installed packs
await manager.update('my-skill-pack');
await manager.uninstall('my-skill-pack');
```

<Warning>
  Skill packs execute inside the agent's system prompt — they're trusted content, not sandboxed code, but a malicious pack can still steer the LLM. `createSkillManager` takes an optional `TrustConfig` to control which sources are allowed and cap how much content a single skill can inject.
</Warning>

## Adding a project skill by hand

Drop a file in `{cwd}/.{appName}/skills/deploy-checklist.md` — no installer needed for something specific to one project, coding or not:

```markdown
---
name: deploy-checklist
version: 1.0.0
description: Pre-deploy checklist
triggers:
  - deploy
  - release
  - ship it
---

Before deploying: run `npm run typecheck`, confirm the CHANGELOG is updated,
and check that no `.env.local` values leaked into the build.
```

It's loaded lazily on the engine's first `run()` — no restart needed to pick up a newly added file, but changes made while a session is already running require a session restart.

## Stack detection (coding usage only)

`SkillActivator.detectStack(cwd)` checks for indicator files (`package.json`→node, `go.mod`→go, `pom.xml`/`build.gradle`→java, `Cargo.toml`→rust, `requirements.txt`/`pyproject.toml`→python, `composer.json`→php, `Gemfile`→ruby, `mix.exs`→elixir) and the result feeds both the skill stack gate and every agent's injected `projectContext`. If you're following Usage 2, you don't need this at all.
