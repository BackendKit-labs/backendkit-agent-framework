[Option A](/examples/orchestrator-agent/standalone-service) ran the whole thing behind one binary — config file in, MCP tool calls out, `executor.ts`/`config.ts`/`run-store.ts` doing the work invisibly. This page builds the same three-department onboarding flow without any of that: only the pieces documented in [orchestrator-agent's library surface](/packages/orchestrator-agent) — `TaskPlanner`, `OpenAICompatibleProvider`/`callLLM`, `consolidateRun` — composed with [`agent-protocol`](/packages/agent-protocol) for dispatch, and your own code for everything the binary would otherwise hide.

## The three specialists, as independent services

Each department is its own deployed `AgentServer` (see [agent-protocol § Server side](/packages/agent-protocol#server-side)) — a real HTTP service, not a config entry. Each exposes one capability, `handle_task`, that runs the request through its own `AgentEngine`:

```ts hr-agent/src/server.ts
import { AgentServer } from '@backendkit-labs/agent-protocol';
import { createBaseEngine, CallbackTransport } from '@backendkit-labs/agent-core';
import type { LLMProvider } from '@backendkit-labs/agent-core';

const provider: LLMProvider = { /* ...OpenAICompatibleProvider or your own, see step 1 */ };

const server = new AgentServer({
  name: 'hr-agent', version: '1.0.0',
  description: 'Creates employee records and sends welcome packets',
  port: 3301,
  apiKey: process.env.AGENT_API_KEY,
});

server.register({
  definition: {
    name: 'handle_task',
    description: 'Run a natural-language HR task',
    async: false,
    input:  { task: { type: 'string', required: true } },
    output: { result: { type: 'string' } },
  },
  execute: async ({ task }) => {
    let result = '';
    const transport = new CallbackTransport((e) => {
      if (e.type === 'token') result += e.content;
    });
    const engine = createBaseEngine({
      agents: [{ id: 'hr', name: 'HR', icon: '🧑‍💼', description: '...', systemPrompt: 'You handle HR onboarding tasks.', allowedTools: [] }],
      providers: { default: provider },
      defaultProvider: 'default',
      defaultAgent: 'hr',
      transport,
    });
    await engine.run(task as string);
    return { result };
  },
});

await server.start();
```

`it-agent/src/server.ts` and `facilities-agent/src/server.ts` are the same shape, different `name`/`port`/`systemPrompt`. Three ports: `3301` (HR), `3302` (IT), `3303` (Facilities).

## The orchestrator script — no `orchestrator.yaml` in sight

```ts orchestrate.ts
import { TaskPlanner, OpenAICompatibleProvider, callLLM, consolidateRun } from '@backendkit-labs/orchestrator-agent';
import { AgentClient } from '@backendkit-labs/agent-protocol';
import { VaultWriter } from '@backendkit-labs/agent-enterprise';
import { randomUUID } from 'node:crypto';

// 1. One shared LLM call, reused for planning and consolidation
const provider = new OpenAICompatibleProvider({ model: 'gpt-4o-mini', api_key: process.env.OPENAI_API_KEY });
const callLLMFn = (system: string, user: string) => callLLM(provider, system, user);

// 2. Duck-typed AgentConfig — not imported (see orchestrator-agent's Warning on this),
//    just an object matching the shape TaskPlanner.plan() expects.
const agents = [
  { id: 'hr',          name: 'HR',          description: 'Employee records, welcome packet', capabilities: ['employee-records'], provider: 'default' },
  { id: 'it',          name: 'IT',          description: 'Accounts and hardware',             capabilities: ['accounts', 'hardware'], provider: 'default' },
  { id: 'facilities',  name: 'Facilities',  description: 'Desk and badge assignment',          capabilities: ['desk-assignment'], provider: 'default' },
];

// 3. Where each agent_id actually lives — this replaces orchestrator.yaml's config entirely
const AGENT_URLS: Record<string, string> = {
  hr:          'http://localhost:3301',
  it:          'http://localhost:3302',
  facilities:  'http://localhost:3303',
};
const clients = Object.fromEntries(
  Object.entries(AGENT_URLS).map(([id, url]) => [id, new AgentClient({ url, apiKey: process.env.AGENT_API_KEY, timeout: 30_000 })]),
);

interface ExecutionResult {
  subtask_id: string; agent_id: string; task: string;
  result: string; success: boolean; duration_ms: number;
}

// 4. Plan
const planner = new TaskPlanner(callLLMFn);
const plan = await planner.plan('Onboard Juan, starting 2026-07-01 as Developer', agents);

// 5. Your own dispatch loop — respects depends_on, runs independent subtasks in parallel.
//    No RunStore, no gates, no BullMQ — just enough to get the three calls out in the right order.
const results = new Map<string, ExecutionResult>();
const pending = new Set(plan.subtasks.map(s => s.id));

while (pending.size > 0) {
  const ready = plan.subtasks.filter(s => pending.has(s.id) && s.depends_on.every(d => results.has(d)));
  if (ready.length === 0) throw new Error('Plan has an unresolvable dependency');

  await Promise.all(ready.map(async (subtask) => {
    const start = Date.now();
    const res = await clients[subtask.agent_id].run('handle_task', { task: subtask.task });
    results.set(subtask.id, {
      subtask_id: subtask.id, agent_id: subtask.agent_id, task: subtask.task,
      result: String((res.output as { result?: string })?.result ?? ''),
      success: res.status === 'done', duration_ms: Date.now() - start,
    });
    pending.delete(subtask.id);
  }));
}

// 6. Consolidate — same helper the binary uses internally, called directly
const learned = await consolidateRun(
  randomUUID(), 'Onboard Juan', [...results.values()], callLLMFn,
  new VaultWriter({ vaultPath: '/shared/vault' }),
);
console.log(learned ? `Learned: ${learned}` : 'Nothing worth consolidating from this run.');
```

## What you gained — and what you now own

<Warning>
  Nothing here checks the `gate: true` a human might want on the `it` step — Option A's binary reads that field off `AgentConfig`/`FlowStep` and pauses; this loop doesn't, because gating logic lives in `executor.ts`, which isn't part of the library surface. If you want approval gates in your own loop, you write that check yourself (e.g. skip dispatching a subtask and surface it to a human before calling `clients[subtask.agent_id].run(...)`) — the framework gives you the planning and dispatch primitives, not the gate semantics built on top of them.
</Warning>

What this bought you, compared to Option A: each specialist is a completely independent, independently-deployable, independently-scaled HTTP service (real `AgentEngine`s, real tools, real memory per specialist — none of which `AgentConfig`'s `id`/`name`/`capabilities` shape can express), dispatched by a loop you fully control. That's the trade the [orchestrator-agent](/packages/orchestrator-agent) page's closing section describes: the binary is the fast path when the config-driven model fits; the library surface is what's left when it doesn't.
