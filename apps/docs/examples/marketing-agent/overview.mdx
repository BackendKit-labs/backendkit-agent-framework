Every other page in these docs explains one building block at a time. This section does the opposite: it takes **one agent** and grows it, step by step, so you can see how the pieces actually combine in a real build — not just in isolation.

The domain is marketing, but nothing here is marketing-specific under the hood. Swap the tools, the skills, and the vault folder, and the same five steps build a support agent, a finance agent, or anything else — that's the point of the framework being domain-agnostic in the first place (see [Why one engine, not one engine per use case](/#why-one-engine-not-one-engine-per-use-case)).

## Where the final code lives

Each step is additive — step 3 imports everything step 2 built, step 4 adds to step 3, and so on. By the end, the project looks like this:

```
marketing-agent/
├── src/
│   ├── tools/
│   │   ├── content.ts        ← draft_social_post, competitor_lookup (step 1)
│   │   └── scheduling.ts      ← schedule_post (step 3)
│   ├── skills/
│   │   └── brand-voice.ts     ← in-code Skill objects (step 2)
│   ├── memory.ts               ← createMemorySystem wiring (step 2)
│   ├── agents.ts                ← AgentProfile roster: lead + specialists (step 3)
│   ├── knowledge.ts             ← ObsidianRAGProvider + VaultWriter (step 4)
│   ├── engine.ts                  ← createBaseEngine, composes everything above
│   ├── repl.ts                     ← terminal entry point (step 5)
│   └── server.ts                    ← MCP server entry point (step 5)
├── .env
└── package.json
```

If you'd rather generate this shape than write it by hand, `create-bk-agent` scaffolds the same layers — see [Agent Types](/getting-started/agent-types) for the equivalent generated output, and [create-bk-agent](/packages/create-bk-agent) for the CLI itself. This walkthrough writes the code directly so every wiring decision is visible.
